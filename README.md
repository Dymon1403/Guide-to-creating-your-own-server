# 2. Настройка BIOS/UEFI:

    HandleLidSwitch=ignore
    HandleLidSwitchExternalPower=ignore

    В runit / elogind (Void Linux):
    Редактируем /etc/elogind/logind.conf и выставляем те же параметры HandleLidSwitch=ignore.

# 3.3.1 Что делать если ноут не поддерживает пороги аккума? 

Итак при запуске sudo tlp-stat -b ты видишь надпись:
Notice: battery charge thresholds not supported for this model. значит твой ноут просто не умеет пользоваться контроллером питания(или его просто тупо нету)

Тут есть 2 варианта:
1. Аппаратный Способ, просто вытащи батарею
2. Программный Способ, тк акуммулятор не умеет контролирвать верхний порог питания, то мы просто будем контролировать нижний порог, чтобы сервер не рубился в ноль когда акум сядет в ноль:
  Когда отключают свет, ноут переходит на батарею. Если свет не дали за 5–10 минут, сервер должен самостоятельно и корректно завершить работу (shutdown), сохраняя все базы данных и конфиги.
# Как это настроить(скрипт-автомат):
1. Создаем скрипт контроля питания
```bash
sudo nvim /usr/local/bin/power-monitor.sh

```
2. Код
```bash
#!/bin/bash

# ПРОВЕРЬ СУКА СВОЙ АКУМ, КАК ОН НАЗЫВАЕТСЯ
# На разных системах может быть AC, ADP1 или ACAD. Проверить можно через: ls /sys/class/power_supply/
AC_STATUS=$(cat /sys/class/power_supply/AC/online 2>/dev/null || cat /sys/class/power_supply/ADP1/online)

# Если AC_STATUS = 0, значит внешнее питание пропало
if [ "$AC_STATUS" -eq 0 ]; then
    # Ждем 3600 секунд
    sleep 3600

    STILL_OFF=$(cat /sys/class/power_supply/AC/online 2>/dev/null || cat /sys/class/power_supply/ADP1/online)

    if [ "$STILL_OFF" -eq 0 ]; then
        # Свет так и не дали - ну все пизда
        /sbin/shutdown -h now 
    fi
fi
```
3. Делаем скрипт исполняемым:
```bash
sudo chmod +x /usr/local/bin/power-monitor.sh

```
4. Закидываем в планировщик (cron), чтобы выполнялся раз в минуту:
```bash
sudo crontab -e

```
окей, с аккумулятором и первоначальной настройкой системы закончили, наша система готова к бою.

# 4. Безопасный SSH-доступ, ключи Ed25519 и изоляция root-пользователя.
1. Генерация криптографических ключей Ed25519. Забудь про логины и стандартные пароли — вход должен быть строго по SSH-ключам. Алгоритм Ed25519 — современный стандарт: он быстрее, безопаснее и компактнее старого RSA
2. На своем основном ПК/ноутбуке (с которого будешь подключаться к серверу) открываешь терминал и генерируешь пару ключей:
```bash
# (Утилита спросит, куда сохранить ключ — жми Enter по умолчанию. Также можно задать кодовую фразу passphrase для дополнительной защиты).
ssh-keygen -t ed25519 -C "main-laptop"

```
3. Копируешь публичный ключ на сервер:
```bash
# (Вместо user — имя твоего пользователя на сервере, вместо 192.168.1.100 — статический IP сервера который ты указывать ранее(пункт 2.2)).
ssh-copy-id -i ~/.ssh/id_ed25519.pub user@192.168.1.100

```
4. Проверяешь чтобы вход был без пароля:
```bash
ssh user@192.168.1.100

```

Шаг 2: Настройка демона SSH (sshd_config)

Теперь, когда вход по ключу настроен, полностью закрываем забор для входа по паролям и логина от имени root:
1. Открываешь конфиг-файл SSH НА СЕРВЕРЕ:
```bash
sudo nvim /etc/ssh/sshd_config

```
2. Находишь (или добавляешь в конец файла) и жестко прописываешь следующие директивы:
```bash
# Запрещаем вход от имени root напрямую
PermitRootLogin no

# Отключаем аутентификацию по обычным паролям (только ключи!)
PasswordAuthentication no
PubkeyAuthentication yes

# Запрещаем пустые пароли
PermitEmptyPasswords no

# Отключаем устаревшие методы аутентификации
KbdInteractiveAuthentication no

# Смена дефолтного порта (по желанию, защищает от тупого скана ботов)
Port 2222
```
3. Сохраняешь файл и проверяешь синтаксис конфига на ошибки перед перезапуском, чтобы не заблокировать сам себя:
```bash
sudo sshd -t

```
Если вывод пустой, то все гуд

4. Перезапускаешь службу SSH:
```bash
sudo systemctl restart ssh

```
5. ВАЖНО: Не закрывая текущую сессию терминала, открой новое окно на рабочем ПК и проверь подключение с учетом нового порта:
```bash
ssh -p 2222 user@192.168.1.100
```

Если планируешь пробрасывать SSH наружу (или просто для защиты в локалке), поставь утилиту fail2ban. Она банит IP-адреса, с которых идут подозрительные или ошибочные попытки авторизации.

# Docker Compose и че, и как, и зачем он нужен?

Поднимать контейнеры через длиннющие команды docker run -p 25565:25565 -v /path:/path -e ENV=true... — это ад. Забудешь один флаг, и всё перенастраивать заново.

Docker Compose позволяет описать всю конфигурацию сервера (порты, папки, переменные) в одном текстовом файле docker-compose.yml - один раз сделал и не ебешь себе мозги

# Главные правила структуры

1. Volumes (Томы): Данные внутри контейнера стираются при его пересоздании. Чтобы миры Майна, конфиги и базы данных сохранялись на диске сервера, мы "пробрасываем" папку с хоста в контейнер:
./data:/data (папка data рядом с файлом манифеста монтируется внутрь контейнера).

2. Ports (Порты): Связываем порт сервера с портом контейнера:
25565:25565 (<Порт_Сервера>:<Порт_Контейнера>).

3. Restart Policy: Прописываем restart: unless-stopped, чтобы при перезагрузке сервера контейнер автоматически поднимался сам.

# Что такое контейнеризация и нахуй она нужна?

Если говорить простым языком, **контейнеризация** - это способ запечатать приложение со всеми его зависимостями, библиотеками и конфигами в один изолированный «контейнер», который запустится на любой Linux-системе абсолютно одинаково.

### Простая аналогия
Представь стандартный морской грузовой контейнер. Внутрь него можно закинуть что угодно — хоть сервер Майнкрафта, хоть базу данных PostgreSQL, хоть веб-сайт. Судну-контейнеровозу (твоему серверу) абсолютно похуй, что лежит внутри — у него есть универсальные крепления (Docker), он просто подхватывает этот блок и запускает его.

### Чем контейнеры отличаются от виртуалок?
* **Виртуальная машина (VirtualBox/KVM):** эмулирует отдельное железо и накатывает сверху целую тяжелую ОС с собственным ядром. Жрет гигабайты ОЗУ тупо на подъем гостевой системы.
* **Контейнер (Docker):** работает напрямую на ядре твоей основной ОС (через механизмы `cgroups` и `namespaces`), изолируя только сам процесс. В итоге контейнер жрет буквально пару мегабайт ОЗУ поверх самого приложения и стартует за 1-2 секунды.

### Почему без Docker на домашнем сервере делать нечего:
1. **Чистота системы:** Ты не засоряешь основную ОС кучей библиотек, пакетов и мусора. Хост-система остается идеально чистой.
2. **Изоляция:** Если сервис внутри контейнера упадет, зациклится или его взломают — он не затронет основную систему и другие контейнеры.
3. **Развертывание в 1 клик:** Все настройки сервиса описываются в одном файле `docker-compose.yml`. Нажал команду - всё поднялось.
4. **Легкое удаление:** Надоел сервис? Удалил контейнер одной командой — и от него не осталось ни одного лишнего файла в системе.


# Практика: Поднимаем сервер Minecraft в Docker; Why noT?_)

Поднимем сервак на базе PaperMC (самое оптимизированное ядро под сплошные лаги и старое железо) с помощью лучшего готового образа itzg/minecraft-server.

1. Создаем структуру каталогов.
   Создадим отдельную папку для сервиса (хорошая привычка — держать все сервисы в /opt/docker/ или в хоум-директории ~/docker/):
```bash
mkdir -p ~/docker/minecraft
cd ~/docker/minecraft

```
2. Создаем docker-compose.yml
```bash
vim docker-compose.yml

```

2.1 И базовую структуру для нашего майнкрафтика:
```bash
version: '3.8'

services:
  mc-server:
    image: itzg/minecraft-server:latest
    container_name: minecraft-server
    tty: true
    stdin_open: true
    restart: unless-stopped
    ports:
      - "25565:25565" # Стандартный порт майна
    environment:
      EULA: "TRUE"              
      TYPE: "PAPER"             
      VERSION: "1.20.4"         
      MEMORY: "3G"              
      MAX_PLAYERS: "10"
      DIFFICULTY: "normal"
      VIEW_DISTANCE: "8"        
      ONLINE_MODE: "FALSE"      
    volumes:
      - ./data:/data            

```

3.1 запуск
```bash
docker compose up -d

```

Ес че Docker сам скачает образ, загрузит PaperMC и сгенерирует мир. Это займет пару минут
Теперь твой сервер Майна крутится в фоновом режиме на порту 25565. Вы можете заходить на него с друзьями внутри локалки по IP-адресу сервера (например, 192.168.1.100:25565).
